# CS2 Demo 分析器

导入 CS2 / CS:GO 的 `.dem` 录像，按**半场**分段、按**队伍**上下分栏统计每个玩家的表现。

## 怎么用

**双击桌面「CS2 Demo 分析器」快捷方式**
→ 点「选择 demo 文件...」→ 选一个 `.dem` → 点「开始分析」。
分析时进度条会按阶段推进，完成后上方用「上半场 / 下半场 / 加时」**勾选**要看哪些阶段
（可以多选，会自动叠加），下方三个页签分别看主要数据、道具伤害、娱乐数据。
上下两队之间的分隔线**可以用鼠标拖动**。随时可以「导出 CSV」。

Windows 默认的 demo 目录：
`...\SteamLibrary\steamapps\common\Counter-Strike Global Offensive\game\csgo\`

- **上下两队**：上面固定是「队伍 1」，下面固定是「队伍 2」。
- **中间那条横线可以用鼠标拖动**，想给哪个队看更多行就往上 / 往下拉。
- **表格里按住鼠标左右拖 = 抓住内容平移**，不用去够横向滚动条。
  （列总宽 978px，上下排列后每张表独占整宽 ~1520px，正常窗口下所有列一次显示完；
  窗口压窄、或者以后列变多时才用得上平移）
- **时间轴同样按住鼠标左右拖**，按在方块或轴线上都能拖；回合少时整条放得下，就不需要拖。
- **上方三个半场选项是复选框，可以多选**：勾几个就把几个阶段合起来看。
- **下方三个页签**：每页都是同样的上下两队，只是指标不同。
- **右边那条「详细信息」栏**：鼠标**悬停**在时间轴卡片上还是老样子，只弹悬浮窗；
  **单击**某张卡片，右边才画出该回合的完整事件时间轴（见下节）。
- 表头可以**拖宽列**；鼠标停在列标题上会弹出该列的含义说明。

### 右侧「详细信息」

单击时间轴上的回合卡片，右侧这一栏显示该回合从头到尾发生了什么：

```
第 18 回合   下半场    比分 6:12    开局 CT = 队伍2
────────────────────────────────────────────────
1:55  5v5  ● 回合开始
1:45  4v5  ● da__shi__(CT) [awp] 有点糕冷-(T)
1:41  4v4  ● 哭泣洋芋(T) [deagle] 枫溪在(CT)
1:25  3v3  ● 离子安(T) [ak47] 来自版纳的大象(CT)
0:25  2v2  ● 下包  春序对弈 豆腐干被问到(T)
0:21  1v2  ● 熟睡的小舅子(CT) [ak47] 离子安(T)
0:00  1v2  ● 拆包  熟睡的小舅子(CT)
0:00  0v2  ● 反恐精英获胜   拆包成功
```

- **时间是从 1:55 倒着算的**，和游戏里的回合计时器一样。
  起点取 demo 里的 `round_freeze_end`（冻结时间结束、开始能行动），
  **不是** `round_start` —— `round_start` 是冻结时间开始的那一刻，
  拿它当起点会把冻结的 20 秒也算进去，时间会一路跑到 2:21 去。
  终点取 `round_end`。
- 提前结束的回合（团灭）停在当时的剩余时间上；第 11 回合正好走到 `0:00`（计时器耗尽）。
  下了包之后回合可以拖过 1:55（炸弹是单独的 40 秒计时），这种就夹在 `0:00`。
- **每行都带当时的存活人数**（`5v5` → `4v5` → …），击杀按发生顺序递减。
- **武器用文字写在方括号里**（`[awp]`），不画图标 —— 理由见「已知限制」。
  排布是紧凑的 `凶手 [武器] 受害者`，不按固定列对齐：名字长短差得远
  （有 9 个字符的英文名，也有 10 个汉字的「春序对弈 豆腐干被问到」），
  对齐会在短名字后面留出上百像素空白，反而不好读。
- **这一栏宽 520px**。这个数字不是随便定的：队伍表格的列加起来需要 981px，
  窗口 1560px 下留给左边的就是 1018px（实测 520px 时表格客户区正好 990px，
  不用出横向滚动条）。再宽一点表格就会被挤出一条横向滚动条。
- **这一栏是白底**，和软件其他区域保持一致，左侧用一条 1px 竖线跟页签区分开。
- **名字按当时所属阵营上色**：CT 蓝 `#2563EB`(37,99,235)、T 橙 `#C2410C`(194,65,12)。
  这两个都是软件里已经在用的队色（CT 蓝和时间轴方块同款）。
  T 用的是深一档的橙而不是方块上的 `#EA580C`(234,88,12)：那个在白底上对比度只有
  3.5:1，深橙是 5.2:1，CT 蓝也是 5.2:1，两边亮度才平衡。
  半场会交换，所以同一个人在上下半场颜色可能不同。
- 左边那条竖轴上的**圆点**同样按归属方上色（回合开始和回合结束用灰色）。
- 行数超出一屏时这一栏自己出滚动条，不影响其他区域。
- **拖动平移时间轴之后的单击不会被当成点卡片。**
  单击判定放在 flow 的 `MouseUp` 里，用 `$d.moved` 区分「拖完松手」和「点一下」——
  详见「实现说明」里关于 `Capture` 吃掉 `Click` 的那条。
- **点中的那一列会在时间轴上标出来**（浅蓝底 `#DBEAFE`，悬停是更浅的 `#EBF2FF`）。
  不然点完卡片只有右边变了，左边完全看不出选的是哪一回合。
  切换半场勾选导致时间轴重建之后，选中标记会自动补回来。
  实现上只改「上一列」和「这一列」两个控件，不重建整条时间轴 ——
  重建要几十毫秒，点一下卡一下。


### 绘制性能

界面上的卡顿基本来自两个地方，都已经处理：

| 问题 | 原因 | 处理 |
|---|---|---|
| 拖动时分隔条 / 时间轴发闪、发卡 | 所有控件的 `DoubleBuffered` 都是 `False`，每个控件直接往屏幕上画 | 建完控件树后统一开双缓冲（`Enable-DoubleBufferTree`）；时间轴的列是动态建的，在 `Render-Timeline` 里单独开 |
| 用一会儿越来越卡 | 详情面板的 `Paint` 里每次重绘都 `New-Object` 4 个 Font、2 个 Pen、每行一个 Brush，结尾只 `Dispose` 了最后一个 Pen，其余全是 GDI 句柄泄漏 | 绘制资源改成只建一次（`$script:DetailGdi`），圆点 Brush 按颜色缓存；时间轴的两个字体同理（`$script:TimelineGdi`） |
| 拖表格内容发涩 | `MouseMove` 里每移一格都遍历一遍 `Columns` 求总宽（PSObject 属性访问，一次约 0.013ms，鼠标一动几百次） | 列总宽在 `MouseDown` 时用原生 `GetColumnsWidth` 算一次，存进 `Tag.totalW` |

实测（1920x1080，19 回合）：

- 详情面板重绘 300 次，GDI 句柄增加 **0**（修复前每次约 +6，300 次约 +1800）
- 分隔条拖动 40 步 **86ms**（每步 2ms）
- 时间轴平移 40 步 **4ms**
- 整个控件树 231 个控件，双缓冲全部为 `True`

注意 `DrawToBitmap` 量出来的「整窗重绘 58ms」**不能**当作真实帧时间：
它走 `WM_PRINT` 强制每个控件渲染一遍，绕过了双缓冲。真实的拖动流畅度提升
主要来自「不再闪」和「不再泄漏句柄」，而不是单次绘制变快。

### 多选时怎么合并

| 类型 | 处理 | 例子 |
|---|---|---|
| **计数类** | **相加（叠加）** | 击杀、死亡、助攻、伤害、爆头、首杀/首死、2K/3K/4K/5K、下包、道具伤害… |
| **派生指标** | **按叠加后的数据重算** | `Rating`、`ADR`、`K/D`、`爆头率%`、`占比%`、`每回合`道具伤害 |

把两个半场的比率直接相加是没有意义的；这里也不是把两个半场的比率取平均，
而是**先叠加原始计数，再按整场口径重算**。实测校验（离子安）：

```
击杀   上半场=16    下半场=8     叠加=24    = 16+8              ✓ 相加
总伤害 上半场=1585  下半场=878   叠加=2463  = 1585+878          ✓ 相加
ADR    上半场=132.1 下半场=125.4 叠加=129.6 = 2463 ÷ 19         ✓ 按叠加重算
Rating 上半场=1.66  下半场=1.33  叠加=1.54  = 用叠加后 K/D/多杀/助攻重算 ✓ 按叠加重算
```

注意 `ADR` 叠加后是 **129.6**，而不是两个半场取平均的 128.75 ——
后者是「两个半场表现的平均」，前者才是「整场口径」，也是 `ADR` 的定义
（总伤害 ÷ 总回合）。`Rating` 同理：用叠加后的击杀/存活/多杀/助攻重算。

界面上的说明文字会跟着显示
「（计数类叠加；Rating / ADR / K/D / 爆头率 / 道具占比 等按叠加后数据重算）」，
和 `Merge-Periods` 的实际逻辑一致。

一个阶段都没勾时，表格会清空并提示「未选择半场」。

## 为什么队伍不写 CT / T

因为**半场会换边**。实测同一个人的 `team_num` 在上下半场是互换的：

```
哭泣洋芋        : 3,3,3,3,3,3,3,3,3,3,3,3, 2,2,2,2,2,2,2   ← 上半场 CT，下半场 T
来自版纳的大象  : 2,2,2,2,2,2,2,2,2,2,2,2, 3,3,3,3,3,3,3   ← 反过来
```

所以用 CT / T 标注会自相矛盾。分析器改成按「**第一次出现在哪一边**」把玩家
固定归入 队伍1 / 队伍2 两个名册，之后无论换到哪边都还属于原名册。
界面上只额外标一行「开局 CT / 开局 T」帮助辨认，不作为队伍名。

## 三个页签的指标

### 主要数据

| 列 | 含义 |
|---|---|
| **Rating** | 见下面「Rating 怎么算」 |
| 击杀 / 死亡 / 助攻 | K / D / A |
| K/D | 击杀 ÷ 死亡 |
| 爆头 / 爆头率% | 爆头击杀数与占比 |
| 总伤害 | 对敌人的**实际掉血**合计（不含队友伤害、不含自伤） |
| ADR | 每回合平均伤害（分母是该阶段**实际参与**的回合数） |
| 首杀 / 首死 | 每回合第一个击杀 / 第一个死亡 |
| 2K / 3K / 4K / 5K | 单回合杀 N 人及以上的回合数 |

> **总伤害为什么要「实际掉血」**：`player_hurt` 事件里的 `dmg_health` 是
> **没有截断的原始伤害** —— AWP 爆头一枪就是 438，可满血只有 100。
> 直接累加等于把溢出伤害（overkill）也算了进去，实测总量会多算 **26%**，
> ADR 跟着一起虚高（`da__shi__` 一局从 175.5 虚高到 107.7 的真实值）。
> 现在用「打之前的血量」做上限：`真实伤害 = min(dmg_health, 打之前剩的血)`，
> 「打之前剩的血」从 `health` 字段反推（它是打完之后的值，所以同一个人上一次的
> `health` 就是这一次的「打之前」，每回合重置为 100）。
> 溢出最多的是 AWP 爆头和大狙打残血：打之前只剩 18 血，那一枪 141 也只算 18。

### Rating 怎么算

近似 **HLTV Rating 2.0**：四个分项各自除以基准值，再加权平均。

```
击杀/回合   基准 0.679      权重 1.5   ← K/D 的主要来源
存活率      基准 0.317      权重 0.7
多杀回合率  基准 0.158      权重 1     （单回合 >=2 杀的回合占比）
助攻/回合   基准 0.106      权重 0.4

Rating = ( 1.5×击杀项 + 0.7×存活项 + 多杀项 + 0.4×助攻项 ) / 3.6
```

除数取 3.6（= 1.5+0.7+1+0.4），这样**四项统计都正好等于基准值的球员恰好是
1.00**，符合「1.00 = 平均水平」的直觉。代码里除数写成
`RATING_DIVISOR = RATING_W_KP + RATING_W_SP + RATING_W_MKP + RATING_W_AP`，
改权重时它会自动跟着变，不会把整体均值推歪。

**权重是怎么调的**：击杀项就是 K/D 在总分里的占比，助攻项则一直在偷偷吃大头
——助攻基准 0.106 偏低，实际每回合助攻常是基准的 3~5 倍。所以两次调整都是
「抬击杀、压助攻」：

| 方案（击杀/助攻） | raw 分里各项占比（击杀/存活/多杀/助攻） | Rating 与 K/D 排名相关性 |
|---|---|---|
| 0.7 / 0.7（最初） | 22.9 / 16.4 / 27.0 / **33.7** | 0.87 |
| 1.2 / 0.7 | 33.0 / 13.7 / 23.6 / 29.7 | 0.90 |
| **1.5 / 0.4（当前）** | **42.3 / 14.0 / 24.8 / 18.9** | **0.98** |

助攻占比从 33.7% 压到 18.9%，击杀项从 22.9% 提到 42.3%，现在是四项里最大的一项。
（相关性是拿本局 10 个人算的，会随对局风格浮动——真正稳定的是**占比**的变化。
另一局 20 回合的数据上，同一组权重给出的是 0.48 → 0.58 → 0.89。）

需要说明的是这是**近似值**，不是 HLTV 官方数字（官方公式没公开到能逐位复现）。
用本局做校验：10 名玩家的平均 Rating = **1.13**，确实落在 1.0 附近，
说明标定没跑偏。单人最高 `da__shi__` 1.68（21/9），最低 0.50。

存活率会夹在 `[0,1]`：回合重启等情况会让死亡数大于回合数（实测有人 12 回合
死 13 次），不夹的话 rating 会算出负数。

> 这个公式在 `src/analyzer.py` 和 `DemoAnalyzer.ps1` 里**各写了一份**
> （分析时算一次、多选半场合并时再算一次），两边必须逐项一致。
> `ratingtest.ps1` 会把 PowerShell 侧的结果交给 Python 用同一套常数重算比对，
> 防止两份实现悄悄漂移。

### 道具伤害

| 列 | 含义 |
|---|---|
| 手雷伤害 | `hegrenade` 造成的伤害 |
| 燃烧伤害 | `inferno` / `molotov` / `incendiarygrenade` / `firebomb` |
| 诱饵伤害 | `decoy` |
| 道具总伤 | 上面三项之和 |
| **占比%** | **道具总伤 ÷（对敌伤害 + 队友伤害）** |
| 每回合 | 道具总伤 ÷ 参与回合数 |
| 手雷击杀 / 燃烧击杀 | 用该道具完成击杀的次数 |
| 闪光助攻 | `assistedflash` 助攻 |

**占比% 是什么**：你打出的**全部伤害**里，有多大比例是靠道具（手雷 / 燃烧 /
诱饵）打出来的。分母同时算上队友伤害，所以它衡量的是「这个人有多依赖道具」。

实测：`离子安` 上半场 道具总伤 36、总伤害 1647、无队友伤害 →
`36 / 1647 = 2.2%`。`来自版纳的大象` 上半场 道具 105、总伤害 1347 →
`7.8%`，说明他是靠雷吃饭的。

### 娱乐数据

| 列 | 含义 |
|---|---|
| 杀鸡 | 击杀小鸡（`other_death` 且 `othertype` 含 `chicken`） |
| 刀杀 | 用刀完成的击杀（武器名含 `knife`） |
| 电击枪杀 | `taser` / `zeus` |
| 下包 / 拆包 | `bomb_planted` / `bomb_defused` |
| 团队击杀 | Teamkill（TK），击杀队友的次数 |
| 自杀 | 自杀或死于世界伤害（掉图、被自己的雷炸死） |
| **团队伤害** | **打在队友身上的伤害合计（友军火力）** |
| 参与回合 | 该阶段实际参与的回合数（也是 ADR 的分母） |

**团队伤害是什么**：你对**队友**造成的伤害总和，也就是友军火力（friendly fire）。
它和「总伤害」是互斥的 —— 总伤害只算敌人，团队伤害只算队友。

**打死队友的那一下也在里面，没有漏算**。这点专门验证过：
`player_hurt` 事件**包含致命的那一击**，所以击杀队友的那一下本来就被统计进去了。
实测一局里 150 次有攻击者的死亡，**全部**都能在同一个 tick 找到对应的 `player_hurt`，
一个都不缺。

所以「团队伤害」是队友伤害的总量：既包含没打死的友军火力，也包含把队友打死的那一下。

> 早先这里还单独列过一栏「TK伤害」＝其中打死人的那一下，后来删掉了。它只是总量的一个
> 子集，而且口径和总量不一致：总量按**实际打掉的血量**截断，TK 那一下取的是武器**原始**
> 伤害、含溢出，低血队友吃到高溢出的一击时，这个子集反而会大于总量。

## 半场怎么切

按 CS2 竞技 / 首选模式的 **MR12** 规则：

```
上半场 = 第 1-12 回合
下半场 = 第 13-24 回合
加时   = 第 25 回合以后
```

录像是 MR15（CSGO）或非标准模式时，分界会不准，需要改
`analyzer.py` 里的 `HALF_ROUNDS` / `REGULATION_ROUNDS`。

### 哪些回合算「正赛回合」

demo 里的 `round_start` 事件并不都是正赛回合。**很多平台（G161、5E 等）赛前
有一段死斗热身**，它也会发 `round_start`，于是事件数多于真实回合数。另外
`m_bHasMatchStarted` 这个标志**在正赛第 1 回合开始时仍然是 `False`**
（要到第 2 回合才翻成 `True`），所以不能拿它当过滤条件——用它会把真正的
第 1 回合整个丢掉，表现为 20 回合的比赛只统计 19 回合、上下半场分界整体
错位一格、时间轴上「CT=A/B」提前一回合换边。

判定只用 `is_warmup_period`：

```python
filt = [t for t in raw_ticks if not is_warmup.get(t, False)]
```

统计口径也统一到「正赛回合」：`compute()` 里的 `keep(tick)` 先要求
`1 <= round_of(tick) <= n_rounds`，`demo.total_kills` 等汇总同样只数落在
正赛回合里的事件。不这样做的后果是「全场」会把赛前死斗的击杀 / 死亡算进来，
**全场 ≠ 上半场 + 下半场 + 加时**（实测差 15 个击杀、11 个死亡，
连 `players` 和 `periods` 两套数字都互相打架）。

## 进度条

`analyzer.py` 会按阶段把进度写进 `out/progress.json`（`{"pct": 0-100, "stage": "..."}`），
客户端在等待时每 80ms 轮询它，驱动进度条和状态文字。阶段划分：

```
2%   打开 demo 文件
7%   读取 demo 头部
12%  读取玩家名单
18%  解析回合与换边
26%  读取击杀事件
34%  解析击杀事件
44%  解析实体死亡事件
52%  解析下包 / 拆包事件
64%  统计击杀 / 死亡 / 助攻
74%  统计道具与娱乐数据
90%  计算汇总指标
96%  写入报告
100% 完成
```

分析在独立进程里跑，主线程一边泵消息一边轮询进度文件，所以进度条会动、窗口不假死。

进度条本身是**自绘**的（`Panel` + `Paint`，在 `Show-Gui` 里），没用系统 `ProgressBar`：
视觉样式会对 `Value` 变化做约 0.3 秒的补间动画，状态栏已经报 100% 了条子还在追，
表现就是「跑到 100 不是满的，要等零点几秒」。自绘版本 `Value` 一变就 `Invalidate`，
当场画满，配色（蓝色渐变）和斜条纹纹理也能自己定。对外仍然暴露
`Value` / `Minimum` / `Maximum`（值存在 `Tag` 里，用 `ScriptProperty` 转发），
调用点和 `clicktest.ps1` 的断言都不用改。

## 实现说明

- 解析用 `demoparser2`（Rust 内核的 CS2 demo 解析库），支持 CS2 的 `PBDEMS2` 格式。
- **玩家以「名字」为主键归并**。SteamID64 超出 float64 精度（>2^53），经 pandas
  读取后末位会漂移（实测差 2），因此 SteamID 只作展示，不用于关联。
- **换边靠每回合采样 `team_num` 解决**：
  `parse_ticks(["team_num"], ticks=round_start_ticks)` 拿到每个回合开始时各人在哪边。
  回合刚开始那一帧少数人取不到值（为 0），要**向前后推断补齐**，否则参与回合数偏少、
  ADR 偏高。
- **回合号用枚举顺序**，不用 `round_start` 的 `round` 列：该列会重复（实测
  `[1,1,2,...,19]`），不可靠。
- 击杀判定用**名册**而不是 CT/T 比大小，换边后依然正确。
- **多选半场是前端合并**，不是在分析器里算的：`Merge-Periods` 把勾选的阶段
  合起来，计数类相加、派生指标按叠加后数据重算。分析器始终输出三个独立阶段 + 一份全场。
- **可拖动分栏用 `SplitContainer`**（`Orientation='Horizontal'`，两个队伍上下排；
  `IsSplitterFixed=$false`）。注意 `Size` / `SplitterDistance` / `Panel1MinSize` /
  `Panel2MinSize` 四个属性互相约束：控件默认尺寸只有 150，直接设会抛
  「SplitterDistance must be between Panel1MinSize and Width - Panel2MinSize」。
  必须先给一个够大的 `Size`，设好 `SplitterDistance` 和最小尺寸，最后才 `Dock='Fill'`；
  居中则放到 `Add_Shown` 里做（那时布局尺寸才是真实的）。**居中的时候方向要对**：
  `Horizontal` 是按 `Height` 对半分，`Vertical` 才是按 `Width` —— 搞反了
  分隔线会跑到角落去。
- **表格左右拖拽平移是自己实现的**：`DataGridView` 没有"抓内容平移"这种能力。
  在 `New-TeamGrid` 里挂了 `MouseDown`/`MouseMove`/`MouseUp`，拖动时改
  `HorizontalScrollingOffset`。三个要点：
  1. 用 **4px 阈值**区分"点一下选中行"和"拖动"，否则单击会被吃掉；
  2. `HitTest` 只在真实单元格上返回 `Cell`，表格下方的空白返回 `None` —— 两种都要放行，
     否则用户拖空白区会以为坏了；表头（`ColumnHeader`）和滚动条要排除，留给系统；
  3. 偏移要手动夹到 `[0, 列总宽 - 可视宽]`，否则会抛 `ArgumentOutOfRangeException`。
- **时间轴是「中间一条轴线 + 上下两排方块」**，不是一格一格的方框：
  **轴上方 = 队伍1 结束时存活人数，轴上 = 回合数 + 获胜方式，轴下方 = 队伍2**。
  每回合是一个 56×58 的**无边框** `Panel`（`BorderStyle='None'`），横向边距为 **0**，
  所以相邻两列首尾相接；每列里那条 `Height=2` 的轴线横跨整列宽，接起来就是
  贯穿整条时间轴的一条连续的线（`tltest.ps1` 会断言相邻列的 `Left` 正好等于
  前一列的 `Right`，有缝隙就报错）。
  存活人数用 **8×8 的方块**表示（一人一个），方块在行里**水平居中**——不居中的话
  相对轴线居中的回合数看起来是歪的。纵向必须**严格镜像**（列高 58、中心 29）：
  上方块行中心 6、下方块行中心 52（29−6 = 52−29 = 23）；
  回合数中心 17、获胜方式中心 41（29−17 = 41−29 = 12）。
  高度是按「不出现纵向滚动条」倒推的：时间轴行 116px，减去 host 上下边距 6、
  host 内边距 8、标题 18、flow 上内边距 4，再预留横向滚动条的 17px，可用 63px，
  列连边距 64px。改列高、边距或行高时要同时核对这个预算，否则纵向滑块会回来
  （`tltest.ps1` 会在「正常宽度」和「压窄到出现横向滚动条」两种状态下都断言没有纵向滚动条）。
- **表格行高必须跟着字体算，不能用 DataGridView 的默认值**：
  `DataGridView` 的默认行高是 **22px**，再减掉 1px 网格线只剩 21px 内容区；
  而 **9.5pt 微软雅黑一行文字的「行盒」实测是 19px**（`TextRenderer.MeasureText`
  的返回值，比 `Font.Height` 的 17 还要大 2px）。两者只差 2px，中文字形的
  上下边缘几乎贴着行框，**笔画底部会被裁掉一点**（用户反馈「表格里的字
  每行上下被切掉一点」「被框挡住」）。
  修法是实测行盒高度再加 8px 呼吸空间：
  ```powershell
  $lineH = [int][Math]::Ceiling([System.Windows.Forms.TextRenderer]::MeasureText('汉字', $Font).Height)
  $g.RowTemplate.Height = $lineH + 8      # 19 + 8 = 27
  $g.ColumnHeadersHeight = $lineH + 8
  ```
  验证方法：把表格 `DrawToBitmap` 成位图，逐 y 数暗像素。行高 23 时文字墨迹
  是 11px（y8-18），行高 27 时变成 13px（y8-21）——**多出来的 y19/y20/y21
  就是原来被裁掉的笔画底部**。预算：27(表头) + 5×27 = 162px，
  上下两个面板（可视高 194 / 189）都放得下 5 名队员，还能再多放 1 行。
- **同一个容器里「填充控件」必须先 Add、停靠边控件必须后 Add**：
  WinForms 的停靠是按 z 序**反着**处理的（后 `Add` 的先停靠）。时间轴这里原本
  先 `Add` 标题再 `Add` flow，结果 flow 先占满整块、标题再压在它上面，
  **时间轴最上面 18px 被标题盖住，第一排方块整个看不见**（用户报的"显示不全"）。
  队伍表格那边写对了还留了注释，时间轴这边漏了。`tltest.ps1` 现在会直接断言
  标题与 flow 的纵向重叠为 0、且 `flow.Top == 标题.Bottom`，防止再犯。
- **时间轴的横向拖动必须挂在列上**：`FlowLayoutPanel` 的子控件会吃掉鼠标事件，
  鼠标按在列上时 flow 收不到 `MouseDown`，拖动就完全失效。所以列和它的每一个
  子控件（轴线、两个标签、两排方块行、每个方块）都挂同一份 `$tlStartPan`，
  按下后把捕获交给 flow，之后的 `MouseMove`/`MouseUp` 自然都落到 flow 上。另外两点：
  1. `AutoScroll` 控件要用 `AutoScrollPosition` 滚动，直接写 `HorizontalScroll.Value`
     不会真正移动视图；`AutoScrollPosition` 取值是负的，记得换算符号。
  2. 位移用 `$s.PointToScreen($e.Location)` 求，不要用全局光标 `MousePosition` ——
     起点在方块上、移动事件落在 flow 上，只有屏幕坐标是同一套参照系（也让测试能模拟）。
- **测试不要用 `SetCursorPos` + `mouse_event`**：那会真的操纵用户的光标。
  `dragtest.ps1` 改用 `SendMessage` 把 `WM_LBUTTONDOWN` / `WM_MOUSEMOVE` / `WM_LBUTTONUP`
  直接发给控件的窗口句柄，并把窗体挪到 `(-4000,-4000)`，用户屏幕上完全无感。
- **给 flow 设了 `Capture` 之后，卡片自己的 `Click` 永远不会触发。**
  `$tlStartPan` 为了拖动会 `$fl.Capture = $true`，鼠标从此归 flow 收，
  卡片再也收不到 `MouseUp`，WinForms 就不会给它发 `Click` ——
  表现就是「点时间轴卡片右侧没反应」。
  所以单击判定放在 `$tlEndPan`（flow 的 `MouseUp`）里自己做命中测试：
  `$fl.GetChildAtPoint($fl.PointToClient($s.PointToScreen($e.Location)))`，
  再读出该控件的 `AccessibleDescription` 拿到回合号。
  **这里的教训在测试方法上**：早先 `detailtest.ps1` 直接反射调 `Control.OnClick`，
  绕过了整条真实输入路径，于是测试全绿、功能却是坏的。
  现在测试按真实序列发 `MouseDown`（落在卡片的子控件上）→ `MouseUp`（发给 flow）。
  凡是「用户点不到」这类问题，测试必须走真实事件序列，不能直接调 `OnXxx`。
- **不要在事件回调里用 `.GetNewClosure()`**：它会把 scriptblock 包进一个动态模块，
  回调里就找不到 `Render-Detail` 这类脚本作用域里的函数了。
  需要「记住」某个值就写到控件属性上（这里用的是 `AccessibleDescription`），
  回调从 `$s` 读回来。
- 反射构造 `MouseEventArgs` / `EventArgs` 时用 `[类型]::new(...)` 或 `[类型]::Empty`，
  **不要用 `New-Object`**：后者返回的对象带 `PSObject` 包装，塞进 `object[]`
  再 `MethodInfo.Invoke` 会抛「无法将 PSObject 转换为 …」。
- 调用 python 走 `Start-Process -WindowStyle Hidden`，**直接起 `python.exe`**。
  不要改回 `cmd.exe /c`：那会新建一个黑色终端窗口。
  也不要依赖 .NET `Process.Start`：受限环境里它会报 `requires elevation`。
- `Start-Process -ArgumentList` 传**数组**时只用空格拼接、不加引号，含空格的路径
  （如 `Counter-Strike Global Offensive`）会被拆成多个参数。所以必须传单个
  已加引号的字符串。
- `analyzer.py` 的结果一律写入 JSON 文件，不依赖 stdout。
- 进度写入采用「先写临时文件再 `os.replace`」，客户端不会读到半截 JSON。
- **界面状态全部放在 `$script:App`**：WinForms 的事件回调是在 `Show-Gui` 返回
  之后才触发的，函数局部变量那时已经不存在，会退化成 `$null` 并抛
  「在此对象上找不到属性」。新增回调时务必照此处理。
  （同理：`Add_Paint` 这类回调里要用 `$script:DetailGdi` 而不是函数里的局部副本。）
- **`$script:App` 里不能写 `[System.Drawing.Color]` 之类的类型名。**
  这个哈希表是在**脚本加载时**构建的，那一刻 `Add-Type -AssemblyName System.Drawing`
  还没执行，写类型名会直接抛「找不到类型 [System.Drawing.Color]」，软件根本起不来。
  需要颜色就存 RGB 分量（如 `TlSelRgb = @(219,234,254)`），用的时候再
  `[System.Drawing.Color]::FromArgb(...)`。
  **这个坑 headless 测试抓不到**：测试脚本自己是先 `Add-Type` 再载入源码的，
  顺序恰好对了，于是全部通过、真实启动才炸。所以「真实启动一次」这一步不能省。
- **函数返回数组时别既写 `return , $x` 又在调用处包 `@()`**：那会得到「数组套数组」，
  后续 `-contains` / `-notcontains` 全部匹配不上。本项目的 bug 就出在这里 ——
  `Get-CheckedPeriods` 曾经返回 `@(@('first'))`，导致合并逻辑认为一个阶段都没勾。
- **`RowStyles.Add` / `ColumnStyles.Add` 返回 int，必须 `[void]` 掉**。否则
  `New-TeamPage` 返回的是 `@(0,1,0,page)` 这种数组，页签名字会变成乱码串。
  （换成 `SplitContainer` 后这条不再触发，但同类的「集合 Add 有返回值」陷阱依然要防。）
- **列顺序变了要同步改按下标取值的代码**：加了 `Rating` 之后「击杀」从 `Cells[1]`
  变成 `Cells[2]`，`SelfTest` 和 `clicktest` 里的合计都要跟着改。
- **`.ps1` 必须保存为 UTF-8 带 BOM**。PowerShell 5.1 对无 BOM 的文件按 GBK 解码，
  中文会全部乱掉并导致大面积语法错误。

## 已知限制

- 小鸡击杀依赖该 demo 里存在 `othertype` 含 `chicken` 的 `other_death` 事件；
  部分 SourceTV 录像里没有小鸡，此时该列为 0（正常现象，不是 bug）。
- 半场分界写死 MR12。非标准模式需要改常量。
- 加时面板在没加时的对局里是空的，会显示「所选中阶段本局没有数据」。
- 队伍名只能叫「队伍 1 / 队伍 2」：demo 里没有可用的队名
  （`team_clan_name` 实测是空串，`team_name` 只有 CT / TERRORIST 这种边名）。
- `Rating` 是近似值，不是 HLTV 官方数字。本局标定结果是平均 1.13（理想 1.00）。
- 派生指标按叠加后的整数计数重算，所以不存在「先各自四舍五入再平均」的
  二次舍入偏差；`K/D`、`ADR` 等只做一次四舍五入。
- 进度阶段是粗粒度的（按解析步骤划分），不是逐帧进度。
- 分析期间不能取消（没有取消按钮）。
- 时间轴只把回合与关键事件列成一列一列（悬停看详情），不能播放回放，也没有热力图。
- 时间轴轴线上只显示回合数与获胜方式，比分与 CT 阵容要悬停看详情；上下两排只画双方结束时
  的存活人数（一人一个方块），不显示具体数值文字。
- **右侧详情里的武器是文字（`[awp]`），没有图标。**
  本来打算画成游戏内的图标，但官方素材压在 CS2 的 `game/csgo/pak01_*.vpk` 里，
  是编译过的 `.vtex` / `.vsvg_c`，本地没有解包工具，机器也连不上外网
  （`Invoke-WebRequest` 到 github 直接超时）。
  退而求其次用 GDI+ 手绘了一套剪影（按步枪 / 狙击枪 / 冲锋枪 / 手枪 / 霰弹枪 /
  机枪 / 刀 / 手雷 / C4 / 电击枪 / 坠落伤害共 11 类画多边形），
  但手绘的轮廓再像也不是原图，同一类里的不同枪（比如 AK 和 M4）长得一样，
  反而容易认错，所以最后决定直接写武器名 —— 更准，也不用维护那套形状数据。
  相关代码已删除（`$script:WeaponShapes` / `Get-WeaponCategory` / `New-WeaponPath`）。
- 右侧详情的时间轴**没有回放能力**，只有「什么时间发生了什么事」。
